# AI 모델 서비스 연결 설계

이 문서는 학습된 KOTE 감정 분석 모델을 백엔드 서비스에 연결하기 위한 기준을 정리한다.

현재 목표는 모델을 바로 서비스에 붙이는 것이 아니라, 어떤 방식으로 붙일지 먼저 명확히 정하는 것이다.

## 1. 연결 목표

사용자가 자연어 문장을 입력하면 백엔드는 아래 순서로 처리한다.

```text
사용자 문장
→ KOTE 감정 모델 예측
→ KOTE 감정 라벨
→ 서비스용 분위기 태그 생성
→ YouTube 검색 키워드 생성
→ 음악 추천 결과 반환
```

모델은 KOTE 감정 라벨만 예측한다.

`mood_tags`와 `search_keywords`는 백엔드 서비스 로직에서 만든다.

## 2. 기존 응답 구조 유지

프론트와 API 구조는 크게 바꾸지 않는다.

현재 응답 구조는 아래 값을 사용한다.

- `input_text`
- `emotions`
- `mood_tags`
- `search_keywords`
- `recommended_tracks`
- `recommended_playlists`

KOTE 모델을 붙이더라도 프론트가 바로 깨지지 않도록 이 구조는 유지한다.

대신 내부 의미를 아래처럼 정리한다.

| 응답 필드 | 의미 |
| --- | --- |
| `emotions` | KOTE 감정 라벨 |
| `mood_tags` | 감정 라벨을 바탕으로 만든 음악 분위기 태그 |
| `search_keywords` | 분위기 태그와 감정 라벨을 조합한 YouTube 검색어 |

## 3. 모델 파일 위치

학습된 모델은 아래 경로에 저장한다.

```text
ml/models/mood-roberta-small/
```

백엔드에서 사용할 때도 우선 이 경로를 기준으로 찾는다.

단, 모델 파일은 Git에 포함하지 않는다.
서비스 실행 환경에서 직접 학습하거나 별도로 전달받아 로컬에 존재해야 한다.

## 4. 모델이 없을 때 fallback

모델 파일이 없으면 백엔드는 실패하지 않고 기존 규칙 기반 분석을 사용한다.

이유:

- 다른 개발 환경에서 모델 파일이 없을 수 있다.
- 모델 파일은 Git에 올라가지 않는다.
- 포트폴리오 시연 중 모델 파일 누락으로 전체 서비스가 멈추면 안 된다.

처리 방식:

```text
모델 파일 있음 → KOTE 모델 사용
모델 파일 없음 → 기존 규칙 기반 분석 사용
```

## 5. 모델 로딩 방식

모델은 요청마다 새로 불러오지 않는다.

권장 방식:

```text
첫 분석 요청
→ 모델 파일 확인
→ 모델 1회 로드
→ 이후 요청에서는 메모리에 올라간 모델 재사용
```

이유:

- 모델 로딩은 느리다.
- 요청마다 모델을 로드하면 응답 시간이 크게 늘어난다.
- 현재 프로젝트 규모에서는 첫 요청 시 lazy loading 방식이 단순하고 충분하다.

## 6. threshold 기준

현재 KOTE 50,000개 전체 학습 모델 기준 평가 결과는 `threshold 0.3`이 가장 좋았다.

따라서 1차 기본값은 아래처럼 둔다.

```text
threshold = 0.3
```

이 값은 고정 정답이 아니다.

이 값은 현재 학습 결과에 맞춘 1차 기준이다.
데이터 구성이 바뀌거나 모델을 다시 학습하면 다시 비교해야 한다.

## 7. KOTE 라벨과 분위기 태그 매핑

KOTE 감정 라벨은 그대로 음악 검색에 쓰기 어렵다.

예를 들어 `힘듦/지침` 라벨이 나오면 YouTube에는 아래와 같은 분위기 검색어가 더 적합하다.

```text
soft quiet warm music
```

따라서 백엔드에는 별도 매핑이 필요하다.

예시:

| KOTE 감정 라벨 | 분위기 태그 |
| --- | --- |
| `힘듦/지침` | `soft`, `quiet`, `warm` |
| `불안/걱정` | `soft`, `quiet`, `warm` |
| `슬픔` | `warm`, `soft`, `late night` |
| `화남/분노` | `heavy`, `uplifting` |
| `짜증` | `heavy`, `uplifting` |
| `행복` | `uplifting`, `light` |
| `기쁨` | `uplifting`, `light` |
| `즐거움/신남` | `uplifting`, `light` |
| `편안/쾌적` | `soft`, `quiet` |
| `안심/신뢰` | `warm`, `soft` |

## 8. 코드 연결 계획

1차 연결 작업은 아래 순서로 진행한다.

1. 백엔드에 KOTE 라벨 → 분위기 태그 매핑 파일을 추가한다.
2. 로컬 모델을 불러오는 모델 어댑터를 추가한다.
3. 모델 파일이 없을 때 기존 규칙 기반 모델로 fallback한다.
4. `predict_analysis()`가 KOTE 모델 결과를 기존 API 응답 구조로 변환한다.
5. 기존 프론트 화면이 깨지지 않는지 확인한다.

## 9. 주의할 점

- 모델 파일은 Git에 올리지 않는다.
- 모델이 없더라도 백엔드가 실행되어야 한다.
- 모델 결과가 항상 좋은 추천으로 이어지는 것은 아니므로 매핑 로직을 따로 개선할 수 있어야 한다.
- threshold는 현재 전체 학습 결과 기준값이며, 모델을 다시 학습하면 다시 평가한다.

## 10. 1차 구현 상태

KOTE 라벨과 분위기 태그 매핑은 `backend/app/ai/mood_mapping.py`에서 관리한다.

현재는 아래 두 종류의 감정 라벨을 모두 처리한다.

- KOTE 한국어 감정 라벨
- 기존 규칙 기반 영어 감정 라벨

이렇게 한 이유는 로컬 학습 모델을 붙이기 전에도 기존 분석 흐름이 깨지지 않게 하기 위해서다.

## 11. 모델 어댑터 구현 상태

KOTE 모델 어댑터는 `backend/app/ai/kote_adapter.py`에서 관리한다.

현재 동작 방식:

```text
모델 파일 있음 + torch/transformers 사용 가능
→ KoteModelAdapter 사용

모델 파일 없음
→ 기존 규칙 기반 AiModel 사용

모델 파일은 있지만 의존성 없음
→ 기존 규칙 기반 AiModel 사용
```

`load_model()`은 `lru_cache`를 사용해 첫 요청에서 선택한 모델을 재사용한다.

이 구조 덕분에 백엔드 요청마다 모델 파일을 다시 읽지 않는다.
