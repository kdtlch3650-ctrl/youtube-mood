# 트러블슈팅

이 문서는 개발 중 만난 문제와 해결 과정을 정리한다.

단순히 결과만 적는 것이 아니라, 어떤 문제가 있었고 왜 문제가 되었는지, 어떤 방식으로 해결하려 했는지를 함께 기록한다.

## 1. 회피 표현이 추천 분위기에 반영되지 않는 문제

### 문제

초기 추천 로직은 모델이 예측한 감정 라벨만 보고 음악 분위기 태그를 만들었다.

예를 들어 모델이 `불안/걱정`을 예측하면 아래처럼 고정된 분위기 태그를 사용했다.

```text
불안/걱정 → soft, quiet, warm
```

이 방식은 기본 감정 흐름을 잡는 데는 사용할 수 있지만, 사용자가 문장 안에서 직접 말한 음악 취향이나 회피 조건을 반영하지 못했다.

예시:

```text
불안하지만 너무 무거운 음악은 싫다
```

이 문장에서는 `불안/걱정`이라는 감정도 중요하지만, `무거운 음악은 싫다`는 조건도 중요하다.

만약 감정 라벨만 보고 추천하면 사용자가 원하지 않는 분위기의 음악이 검색될 수 있다.

### 원인

AI 모델의 역할과 추천 후처리 로직의 역할이 분리되어 있었기 때문이다.

현재 KOTE 모델은 사용자의 감정 라벨을 예측한다.

```text
사용자 문장 → KOTE 감정 라벨
```

하지만 모델이 아래와 같은 추천 조건까지 직접 판단하는 구조는 아니었다.

```text
무거운 음악은 싫다
너무 슬픈 노래는 피하고 싶다
신나는 음악은 부담스럽다
```

즉, 모델은 감정을 예측하지만 추천에서 피해야 할 분위기는 별도로 처리해야 했다.

### 해결 시도

백엔드 후처리 단계에 문장 기반 분위기 태그 보정 로직을 추가했다.

처리 흐름:

```text
감정 라벨 예측
→ 감정 라벨 기반 기본 mood_tags 생성
→ 사용자 문장 안의 회피 표현 확인
→ 피해야 할 분위기 태그 제거
→ 더 적합한 분위기 태그 추가
→ search_keywords 생성
```

예시 규칙:

```text
무거운 + 싫다
→ heavy, late night 제거
→ soft, light 추가
```

적용 예시:

```text
입력: 불안하지만 너무 무거운 음악은 싫다
```

보정 후 결과:

```text
mood_tags: soft, light, quiet, warm
search_keywords: soft emotional music, light feel good music, quiet calm playlist
```

### 현재 한계

현재 회피 표현 처리는 AI 모델이 아니라 규칙 기반 키워드 매칭이다.

장점:

- 동작 이유를 설명하기 쉽다.
- 어떤 표현 때문에 태그가 바뀌었는지 추적하기 쉽다.
- 현재 프로젝트 규모에 맞게 단순하다.

한계:

- 키워드 목록에 없는 표현은 놓칠 수 있다.
- 문맥을 깊게 이해하지는 못한다.
- 표현이 다양해질수록 규칙을 계속 보완해야 한다.

향후 개선한다면 회피 표현을 별도 분류 모델이나 LLM 판단으로 분리할 수 있다.

## 2. KOTE 원본 라벨 모델의 성능 한계

### 문제

KOTE 원본 감정 라벨 전체를 그대로 학습한 모델의 성능이 기대보다 높지 않았다.

전체 50,000개 데이터 학습 후 검증 데이터 10,000개 기준 결과:

| threshold | precision_micro | recall_micro | f1_micro | f1_macro |
| --- | --- | --- | --- | --- |
| `0.3` | `0.5787` | `0.6835` | `0.6268` | `0.3001` |

`f1_micro`는 1차 모델로 사용할 수 있는 수준이지만, `f1_macro`가 낮았다.

이 말은 자주 나오는 감정 라벨은 어느 정도 맞추지만, 드물거나 세부적인 감정 라벨은 잘 맞추지 못한다는 뜻이다.

### 원인

KOTE 원본 라벨은 음악 추천 목적에 비해 너무 세부적이다.

예를 들어 아래 라벨들은 사람도 구분하기 애매할 수 있다.

```text
슬픔
서러움
안타까움/실망
절망
```

또한 한 문장에 여러 감정 라벨이 동시에 붙는 멀티라벨 구조라서 학습 난도가 높다.

문제 요약:

- 감정 라벨 수가 많다.
- 비슷한 감정 라벨이 많다.
- 라벨별 데이터 수가 불균형하다.
- 음악 추천에는 세부 감정보다 큰 감정 방향이 더 중요할 수 있다.

### 해결 시도

KOTE 원본 라벨을 음악 추천에 필요한 감정 그룹으로 묶는 실험을 시작했다.

기존 방식:

```text
사용자 문장
→ KOTE 세부 감정 라벨 예측
→ mood_tags로 변환
```

실험 방식:

```text
사용자 문장
→ 추천용 감정 그룹 예측
→ mood_tags로 변환
```

1차 그룹 라벨:

```text
anxiety
sadness
tiredness
irritation
positive
comfort
focus
neutral
```

1000개 샘플 기준 실험 결과:

| threshold | precision_micro | recall_micro | f1_micro | f1_macro |
| --- | --- | --- | --- | --- |
| `0.3` | `0.5866` | `0.7515` | `0.6589` | `0.5479` |

샘플 실험에서는 세부 KOTE 라벨 모델보다 `f1_macro`가 높게 나올 가능성을 보였다.

### 전체 학습 후 결과

그룹 라벨 모델을 전체 50,000개 데이터로 다시 학습했다.

전체 검증 데이터 10,000개 기준 결과:

| threshold | precision_micro | recall_micro | f1_micro | f1_macro |
| --- | --- | --- | --- | --- |
| `0.2` | `0.6345` | `0.8609` | `0.7306` | `0.6399` |
| `0.3` | `0.6811` | `0.8051` | `0.7379` | `0.6401` |
| `0.4` | `0.7203` | `0.7542` | `0.7369` | `0.6284` |
| `0.5` | `0.7540` | `0.7028` | `0.7275` | `0.6101` |

기존 KOTE 원본 라벨 모델과 비교하면 아래와 같다.

```text
기존 KOTE 원본 라벨 모델
threshold 0.3
f1_micro 0.6268
f1_macro 0.3001

그룹 라벨 모델
threshold 0.3
f1_micro 0.7379
f1_macro 0.6401
```

### 현재 판단

그룹 라벨 방식은 음악 추천 목적에는 더 적합할 가능성이 있다.

전체 학습 기준에서도 기존 KOTE 원본 라벨 모델보다 성능이 높게 나왔다.

특히 `f1_macro`가 크게 개선되었기 때문에, 세부 라벨 불균형 문제를 줄이는 데 효과가 있었다고 볼 수 있다.

다만 이 결과만으로 바로 기존 모델을 교체하지는 않는다.
다음 단계에서는 그룹 라벨 모델을 백엔드 추천 로직에 연결해 실제 추천 결과가 더 자연스러운지 비교해야 한다.

### 현재 한계

- 그룹 라벨 매핑 기준은 1차 초안이다.
- 어떤 KOTE 라벨을 어떤 그룹에 넣을지 더 다듬을 수 있다.
- 그룹 라벨 모델이 좋아지더라도 세부 감정 설명력은 줄어든다.
- 최종적으로는 추천 품질과 모델 평가 지표를 함께 봐야 한다.

## 3. 사용자가 말한 장르가 추천 검색어에 반영되지 않는 문제

### 문제

사용자가 자연어 문장 안에 특정 장르를 직접 말해도, 기존 검색어는 감정과 분위기 태그만 기준으로 만들어졌다.

예시:

```text
오늘 좀 지치는데 너무 우울하지 않은 재즈 음악 듣고 싶어
```

기존 흐름에서는 `지침`, `우울하지 않음` 같은 감정과 분위기는 반영할 수 있었지만, `재즈`라는 장르는 검색어에 직접 들어가지 않았다.

그 결과 사용자는 재즈를 원했는데도 YouTube 검색어가 아래처럼 만들어질 수 있었다.

```text
soft emotional music
light feel good music
quiet calm playlist
```

### 원인

감정 분석 모델의 역할과 음악 장르 처리의 역할이 분리되어 있지 않았다.

AI 모델은 사용자의 감정 방향을 예측하는 데 사용한다.
반면 `재즈`, `힙합`, `발라드` 같은 장르는 감정이라기보다 사용자가 직접 지정한 음악 조건이다.

장르까지 AI 감정 모델이 판단하게 만들면 아래 문제가 생긴다.

- 모델 라벨 구조가 복잡해진다.
- 감정과 장르의 역할이 섞인다.
- 장르 하나를 추가할 때마다 학습 데이터나 라벨 구조를 다시 고민해야 한다.
- 사용자가 이미 장르를 직접 말했는데도 모델 예측에 의존하게 된다.

### 해결 시도

장르는 AI 모델이 아니라 백엔드 규칙 기반 로직에서 별도로 추출하도록 분리했다.

처리 흐름:

```text
사용자 문장
→ AI 감정/분위기 분석
→ 입력 문장에서 장르 키워드 추출
→ 분위기 태그 + 장르를 조합해 YouTube 검색어 생성
```

예시:

```text
입력: 오늘 좀 지치는데 너무 우울하지 않은 재즈 음악 듣고 싶어
장르: jazz
mood_tags: soft, light, warm
search_keywords: soft jazz music, soft jazz playlist, light jazz music
```

### 현재 판단

현재 프로젝트 규모에서는 규칙 기반 장르 추출이 가장 단순하고 적절하다.

이 방식은 장르를 감정 모델에 억지로 넣지 않기 때문에 역할이 명확하다.

- AI 모델: 감정과 분위기 방향 예측
- 장르 추출 로직: 사용자가 직접 말한 음악 장르 확인
- 검색어 생성 로직: 분위기와 장르를 조합

### 현재 한계

- 등록된 장르 키워드만 인식한다.
- 여러 장르가 동시에 들어오면 먼저 나온 장르 하나만 사용한다.
- 문맥상 장르가 아닌 단어를 장르로 오해할 가능성이 있다.

처음 버전에서는 대표 장르만 지원하고, 실제 테스트 중 자주 쓰는 장르를 조금씩 추가하는 방식이 적절하다.

## 4. 장르 키워드를 잘못 인식할 수 있는 문제

### 문제

장르 키워드를 늘리면 사용자가 의도하지 않은 단어를 장르로 잘못 인식할 수 있다.

예를 들어 아래 단어들은 음악 장르이기도 하지만 일반 단어로도 쓰일 수 있다.

```text
house
dance
trap
folk
pop
rock
indie
```

단순히 문장 안에 해당 단어가 있는지만 확인하면 아래 같은 오탐이 생길 수 있다.

```text
집에서 쉬고 싶어
```

이 문장을 영어 입력으로 바꿨을 때 `house`가 들어간다고 해서 무조건 하우스 음악을 원하는 것은 아니다.

또한 `춤추고 싶은 기분`은 댄스 장르를 원한다는 뜻일 수도 있지만, 단순히 밝고 신나는 분위기를 말하는 것일 수도 있다.

### 원인

기존 장르 추출 방식은 키워드 존재 여부만 확인했다.

```text
문장 안에 장르 단어가 있음
→ 장르로 확정
```

이 방식은 `재즈`, `로파이`, `클래식`처럼 장르성이 강한 단어에는 잘 맞는다.

하지만 `house`, `dance`, `pop`처럼 다른 의미로 쓰일 수 있는 단어에는 위험하다.

### 해결 시도

장르를 두 그룹으로 나누었다.

```text
safe genres
→ 단어 자체가 장르 의미로 쓰일 가능성이 높은 장르

ambiguous genres
→ 일반 단어와 겹칠 수 있어 문맥 확인이 필요한 장르
```

`safe genres`는 기존처럼 키워드가 있으면 장르로 인정한다.

예시:

```text
재즈 듣고 싶어
→ jazz

로파이 음악 추천해줘
→ lofi
```

`ambiguous genres`는 음악 관련 문맥이 함께 있을 때만 장르로 인정한다.

음악 관련 문맥 예시:

```text
음악
노래
곡
플레이리스트
듣고
추천
music
song
playlist
track
```

예시:

```text
house music 듣고 싶어
→ house

하우스 음악 추천해줘
→ house
```

반대로 음악 문맥이 부족하면 장르로 확정하지 않는다.

### 현재 판단

현재 프로젝트에서는 별도 장르 분류 AI를 만드는 것보다 규칙 기반 문맥 확인이 더 적절하다.

이유:

- 구현이 단순하다.
- 오탐 원인을 설명하기 쉽다.
- 장르 추가와 수정이 빠르다.
- 감정 모델의 역할을 복잡하게 만들지 않는다.

### 현재 한계

- 문맥 규칙에 없는 표현은 놓칠 수 있다.
- 애매한 장르를 너무 엄격하게 잡으면 사용자가 의도한 장르도 인식하지 못할 수 있다.
- 여러 장르가 동시에 들어오면 여전히 먼저 나온 장르 하나만 사용한다.

이후 실제 입력 테스트를 보면서 `safe`와 `ambiguous` 분류를 조정하는 방식으로 개선한다.

## 5. 검색 결과가 해외 결과에 치중되는 문제

### 문제

자연어 입력 후 추천 결과를 확인했을 때 해외 곡이나 해외 플레이리스트가 많이 노출되는 문제가 있었다.

특히 사용자가 한글로 입력했거나 한국어 음악도 기대할 수 있는 상황에서도 결과가 영어권 콘텐츠에 치우치는 경우가 있었다.

처음에는 검색 옵션에 `한국어 중심`을 추가하고 YouTube API 요청에 아래 값을 넣는 방식으로 해결하려 했다.


```text
regionCode=KR
relevanceLanguage=ko
```

하지만 이 값들은 검색 결과를 강제로 한국어 콘텐츠로 제한하는 필터가 아니다.
YouTube에 한국 지역과 한국어 결과를 더 고려해 달라고 전달하는 힌트에 가깝다.

### 원인

YouTube 검색 결과는 지역이나 언어 옵션보다 실제 검색어의 영향을 더 크게 받는다.

기존 검색어는 대부분 영어로 만들어졌다.

예시:

```text
warm comfort dance music
warm comfort dance playlist
soft dance music
```

이 상태에서는 `regionCode=KR`, `relevanceLanguage=ko`를 추가해도 YouTube가 여전히 영어 검색어와 글로벌 인기 결과를 강하게 반영할 수 있다.

즉 문제는 검색 옵션만의 문제가 아니라 검색어 언어의 문제도 함께 있었다.

### 해결 시도

`한국어 중심` 옵션을 선택했을 때 실제 YouTube 검색어도 한국어 중심으로 만들도록 변경했다.

처리 방식:

```text
전체
→ 기존 영어 검색어 사용

한국어 중심
→ mood_tags와 genre를 한국어 검색어로 변환
→ YouTube API에는 regionCode=KR, relevanceLanguage=ko도 함께 적용
```

예시:

```text
genre: dance
mood_tags: warm, soft, uplifting, light
```

기존 검색어:

```text
warm comfort dance music
```

한국어 중심 검색어:

```text
따뜻한 댄스 음악
```

### 현재 판단

해외 결과 치중 문제는 단순 API 옵션만으로는 효과가 약하다.

따라서 아래 두 가지를 함께 적용하는 것이 더 적절하다.

- YouTube API 지역/언어 옵션
- 한국어 검색어 생성

이 방식은 사용자가 `한국어 중심`을 선택했을 때만 적용되므로, 기본 추천 결과가 한국 곡으로 과하게 치우치는 문제도 줄일 수 있다.

### 현재 한계

- 한국어 검색어 매핑은 1차 초안이다.
- 같은 `warm` 태그라도 상황에 따라 `따뜻한`, `편안한`, `잔잔한` 중 어떤 표현이 더 나은지 달라질 수 있다.
- YouTube API가 한국어 검색어를 사용해도 한국 곡만 반환한다고 보장할 수는 없다.

이후 실제 검색 결과를 보면서 한국어 표현을 조정해야 한다.

## 14. Cognito 로그인 중단

### 문제

Google 로그인에 Cognito를 붙여서 처리하려고 했지만, 공개 배포 주소에서는 HTTPS가 필요했다.
그런데 이 프로젝트는 무료 범위 안에서 먼저 진행하고 있었기 때문에, Route 53이나 별도 도메인 없이 HTTPS를 바로 붙이기 어려웠다.

### 판단

- 개발 단계에서는 Cognito 설정이 너무 복잡했다.
- 배포 주소가 HTTP인 상태에서는 로그인 흐름이 깨졌다.
- `digest` 오류, `invalid_scope`, `invalid_client`, `invalid_grant` 같은 문제가 연달아 발생했다.

### 정리

그래서 Cognito 방식은 잠시 중단하고, 나중에 더 단순한 로그인 방식으로 다시 정리하기로 했다.

현재 방향은 다음과 같다.

```text
Google 로그인 단순화
→ Cognito 제거
→ 배포 환경에서도 동작하는 최소 인증 구조로 재정리
```

### 남은 기준

- 로그인은 너무 복잡한 설정보다 단순한 흐름을 우선한다.
- 배포 환경에서 HTTPS가 필요한 구조는 나중에 다시 검토한다.
- 지금 단계에서는 인증보다 추천/기록/배포 안정성을 우선한다.
