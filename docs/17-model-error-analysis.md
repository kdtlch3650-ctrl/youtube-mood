# 모델 오류 분석 정리

## 1. 문서 목적

이 문서는 자연어 감정 분석과 음악 추천 과정에서 반복해서 발생한 문제를 시간 순서대로 정리한 문서다.

기능 이름을 따로따로 나열하기보다, `무슨 문제가 있었는지`, `어떤 방식으로 바꿨는지`, `결과가 어떻게 달라졌는지`를 한 흐름으로 묶어서 적는다.

---

## 2. 중복 표현 정리 기준

아래 표현들은 따로 쓰지 않고 같은 묶음으로 정리한다.

- `모델 변경`
  - 로컬 모델 연동, grouped 모델 우선 적용, fallback 구조를 모두 포함한다.
- `Bedrock 추가`
  - 감정문/요청문 분리, 부정 표현 보강, 요청 키워드 추출을 포함한다.
- `후처리 보강`
  - 회피 표현 처리, blocked mood tag 처리, 검색어 재구성을 포함한다.
- `검색 키워드 재구성`
  - 감정 태그만 쓰지 않고 요청 표현과 장르 힌트를 함께 반영하는 단계다.

즉, 같은 의미를 다른 이름으로 반복하지 않고 하나의 단계 안에 역할을 같이 적는 방식으로 정리한다.

---

## 3. 진행 흐름

### 3.1 1차: 기본 모델 구조 정리

#### 문제

처음에는 규칙 기반 분석만으로 감정과 요청을 함께 처리하려고 했다.
하지만 복합 감정이나 상황 설명이 들어간 문장에서는 한 번에 정확한 분리가 어려웠다.

#### 해결

로컬 모델을 우선 사용하되, 없을 때는 규칙 기반으로 fallback 하는 구조를 만들었다.

또한 grouped 모델이 있으면 먼저 사용하고, 없으면 일반 KOTE 어댑터를 쓰는 순서로 정리했다.

#### 결과

- 모델 선택 순서가 분명해졌다.
- 모델이 없을 때도 분석이 완전히 멈추지 않게 됐다.
- 같은 입력에 대해 더 안정적인 기본 추론이 가능해졌다.

---

### 3.2 2차: Bedrock으로 감정문과 요청문 분리

#### 문제

사용자 문장에는 감정과 요청이 같이 들어가는 경우가 많았다.

예를 들면:

- `오늘은 지치고 힘들어서 지루한 곡은 듣고 싶지 않아`
- `편안한 기분이야 하지만 너무 지루한 곡은 듣고 싶지 않아 댄스곡이였으면 좋겠어`

이런 문장은 감정만 보면 `슬픔`, `피곤함` 쪽으로 가지만, 실제 검색 의도는 `지루하지 않은`, `댄스`, `빠른`, `가벼운` 쪽일 수 있다.

#### 해결

Bedrock을 먼저 사용해서 문장을 감정 표현, 요청 표현, 부정/회피 표현으로 나누게 했다.

그 다음 로컬 규칙으로 한 번 더 보강해서, 분리 결과가 부족할 때도 검색에 필요한 표현을 놓치지 않도록 했다.

#### 결과

- 감정만 읽는 문제가 줄었다.
- 사용자가 실제로 원한 분위기와 요청이 더 잘 드러났다.
- `감정문 / 요청문 / 부정문`이 분리되어 후속 처리하기 쉬워졌다.

---

### 3.3 3차: 회피 표현과 부정 표현 후처리

#### 문제

모델이 `싫다`, `말고`, `지루한 건 싫어`, `너무 무거운 건 듣고 싶지 않아` 같은 표현을 그대로 잘 반영하지 못했다.

그 결과 추천 결과가 너무 어둡거나, 사용자가 원하지 않는 분위기로 치우칠 때가 있었다.

#### 해결

후처리 단계에서 회피 표현을 따로 잡아 `blocked mood tags`와 `avoid mood tags`로 정리했다.

예를 들면:

- `지루한 곡은 듣고 싶지 않아` -> `heavy`, `late night` 계열 제거
- `너무 무거운 음악은 싫다` -> `soft`, `light` 쪽 우선

#### 결과

- 원치 않는 분위기 추천이 줄었다.
- 같은 감정이라도 표현 방식에 따라 결과를 다르게 조정할 수 있게 됐다.
- 모델 결과를 그대로 믿지 않고, 문장 의도를 반영하는 구조가 생겼다.

---

### 3.4 4차: 검색 키워드 재구성

#### 문제

감정 태그만 검색어로 쓰면 결과가 너무 단순해졌다.

예를 들어 `sad`나 `calm`만 기준으로 검색하면 실제 사용자가 원한 `댄스`, `빠른`, `지루하지 않은`, `한국어 중심` 같은 조건이 빠질 수 있었다.

#### 해결

검색 키워드는 다음을 함께 조합하도록 정리했다.

- 감정 태그
- 요청 표현
- 장르 힌트
- 회피 표현에서 나온 제외 조건
- 한국어 / 전체 검색 범위

#### 결과

- 검색 결과가 감정만 따라가는 문제가 줄었다.
- 사용자의 문장 전체가 검색 키워드에 더 잘 반영됐다.
- 추천 결과가 단순 감정 분류보다 자연스러워졌다.

---

### 3.5 5차: 테스트 케이스 보강

#### 문제

문장 해석 방식이 바뀔 때마다 결과가 달라질 수 있어서, 감으로만 확인하면 어떤 변경이 실제로 영향을 줬는지 추적하기 어려웠다.

#### 해결

대표 테스트 문장을 만들어서 계속 확인했다.

예를 들면:

- 감정만 있는 문장
- 요청이 섞인 문장
- 회피 표현이 있는 문장
- 장르가 들어간 문장
- 한국어 중심 검색이 필요한 문장

#### 결과

- 로직 수정 전후를 비교하기 쉬워졌다.
- 어떤 변경이 도움이 됐는지 확인할 수 있게 됐다.
- 문장 해석이 흔들릴 때 원인을 찾기 쉬워졌다.

---

## 4. 실제 구조 요약

현재 구조는 아래 순서로 이해하면 된다.

```text
사용자 입력
→ Bedrock 또는 로컬 규칙으로 감정문 / 요청문 / 부정문 분리
→ 로컬 모델로 감정 추론
→ 후처리로 회피 표현, 선호 표현, 장르 힌트 보강
→ 검색 키워드 재구성
→ YouTube 검색
```

이 문서에서 말하는 변경은 대부분 이 흐름 안에서 일어난 것이다.

---

## 5. 지금까지의 핵심 결론

- `모델 변경`만 있었던 것은 아니다.
- `Bedrock 추가`, `로컬 모델 연동`, `후처리 보강`, `검색 키워드 재구성`이 함께 바뀌었다.
- 같은 내용을 다른 이름으로 반복하지 않도록 하나의 흐름으로 묶어서 적는 것이 맞다.
- 다음 문서에서는 기능 이름보다 `문제 → 해결 → 결과` 형태로 적는 편이 읽기 쉽다.
- 시간순으로 보면 `기본 구조 → Bedrock 분리 → 회피 표현 보강 → 검색 키워드 재구성 → 테스트 보강` 순서다.
